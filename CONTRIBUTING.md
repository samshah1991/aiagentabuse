# Contributing

Thanks for helping document AI agent incidents. Please read the [method](https://aiagentabuse.com/method/) first.

## Ground rules

- **Real incidents only**, with at least one public source. No hypotheticals presented as fact.
- **Paraphrase.** Summaries are 2-4 sentences in your own words. No long quotations.
- **Defensive only.** No exploit code, working attack payloads, or step-by-step attack instructions.
- **Responsible disclosure.** Do not submit unpatched vulnerabilities. Report them to the vendor first.
- **No private data.** No secrets, credentials, or personal data about private individuals.
- **Human review.** Nothing generated by an AI agent is published without a human checking it.

## Submitting an incident (no code needed)

Open an issue using the **Submit an incident** form (`.github/ISSUE_TEMPLATE/incident.yml`). A maintainer will triage it.

## Submitting via pull request

1. Add `data/incidents/<id>.yaml` following the schema in the README.
2. Set `verification_status: draft`.
3. Run `npm run validate` and `npm run build`.
4. Open a pull request and link the related issue, if any.

## Review process

1. **Triage** (maintainer): in scope? Track and category plausible? Sources public? Label `accepted`, `needs-info`, or `out-of-scope`.
2. **Draft**: a contributor or maintainer opens a PR with a `draft` entry.
3. **Source check** (human reviewer, not the author): open every source, confirm each claim in the summary and impact, confirm the date, and check that wording is paraphrased.
4. **Taxonomy check**: confirm track, category, OWASP ID, and severity.
5. **Verify**: the reviewer sets `verification_status: verified` and `last_reviewed` to today, then merges.
6. **Corrections**: open an issue or PR with evidence. Material changes set `verification_status: corrected` and update `last_reviewed`.

Rule of thumb: the person who sets `verified` must not be the person (or agent) who drafted the entry.

## Severity guide

- **low**: minor inconvenience, quickly reversed, no data exposure.
- **medium**: limited data exposure or disruption, recoverable.
- **high**: significant data loss, exposure, financial loss, or downtime.
- **critical**: large-scale or irreversible harm, or exposure of highly sensitive data.

## Code changes

Keep the site static, free to host, and free of cookies, trackers, and third-party scripts or fonts. Run `npm run build` before opening a PR.
